Preguntas sobre HTTP

1) ¿Sobre qué protocolo binario está montado HTTP?

Sobre TCP (y este sobre IP). El servidor tiene un socket pasivo escuchando en el par IP-puerto 80, y la conexión se establece después de un handshaking de 3 vías (solicitud, aceptación y confirmación). En HTTPS se agrega TLS entre HTTP y TCP. En HTTP/3 esto cambia: va montado sobre QUIC, que corre sobre UDP.

2) Clientes y servidores HTTP más utilizados

Clientes: el navegador, cURL, y las librerías nativas de distintos lenguajes de desarrollo.

Servidores: los web servers (Apache es el ejemplo del apunte, en el header Server: Apache/1.2). Ojo con la aclaración del final: Tomcat no es un web server, es una JVM que interpreta bytecode Java.

3) Verbos que admite el requerimiento

  • GET → solo lectura

  • POST → normalmente para actualizar recursos

  • PUT → para crear recursos en el servidor

  • DELETE → para borrar recursos

  • CONNECT → lo usan los proxies

Se usan como verbos para manipular recursos remotos en servicios web (DELETE /clientes/marcos HTTP/1.1).

4) ¿Qué contenido lleva el body de un requerimiento?

Puede llevar datos en cualquier formato, típicamente:

  • datos ingresados en campos de un formulario

  • archivos enviados en un proceso de upload

Y va acompañado de headers que lo describen: Content-Type (tipo/charset) y Content-Length (longitud de lo transmitido hacia el servidor).

5) Diferencia entre URL y URI

La URI es solo el identificador del recurso dentro del servidor: /path_al_recurso/index.html?var1=valor1&var2=valor2. Es lo que viaja en la línea inicial del requerimiento.

La URL es lo que ves en la barra del navegador y es el conjunto: http://nombreHost.dominioHost:puerto + URI. Esa parte extra (protocolo, host, dominio, puerto) es la que el navegador necesita primero para consultar la IP al DNS y después para establecer la conexión TCP.

6) ¿Cómo se almacena información relacionada con las respuestas?

Dos mecanismos:

  • Cookies: el servidor manda Set-cookie: en la respuesta, el navegador guarda ese dato y lo reenvía con el header Cookie: en los siguientes requerimientos al mismo servidor/origen.

  • Cache del navegador, controlado por headers de respuesta (Cache-control, Expires, Last-Modified, ETag) y validado con headers de requerimiento (If-Modified-Since, If-None-Match).

7) ¿Qué significa HTTP sobre conexiones preexistentes?

Son las conexiones persistentes de HTTP/1.1: se abre una sola conexión TCP y sobre ella se hacen múltiples transacciones (se pide el recurso principal y después imágenes, CSS, JS...) hasta el último recurso, sin reabrir conexión cada vez. Se pide con Connection: keep-alive. Esto es lo que habilita el HTTP asincrónico (AJAX). Se corta con Connection: close (lo puede mandar el cliente, por ejemplo al cerrar el navegador, o el servidor tras un time out de inactividad).

8) ¿Qué significa Virtual hosting?

Que un mismo web server con una única IP puede atender múltiples dominios. Por eso en HTTP/1.1 el header Host: es obligatorio: es lo único que le dice al servidor a qué host virtual le estás hablando. Requiere declarar el nombre en un DNS público (normalmente lo hace el ISP que hostea) y configurar el web server para host virtuales. Para simularlo localmente se edita \windows\system32\drivers\etc\hosts.

9) ¿Qué significa cache por ETag?

El ETag es un identificador tipo fingerprint/hash asociado a cada archivo en el servidor, que cambia cada vez que el recurso se modifica. El navegador lo recibe en la cabecera de la respuesta y lo guarda; en el siguiente acceso a esa URL lo manda como If-None-Match: ead145f. El servidor compara ese header con el ETag actual del recurso: si no cambió, responde 304 Not Modified (1KB en vez de 100KB) y el navegador carga desde su cache.

Ventaja sobre el cache por fechas (If-Modified-Since / Last-Modified): no depende de errores de configuración de fecha entre servidor y cliente, cosa importante porque el desarrollador normalmente no controla el SO del servidor.

10) ¿Por qué HTTP se considera stateless?

Porque el protocolo no guarda estado entre requerimientos: cada mensaje es independiente y, al no haber más conexión, cualquier aplicación pierde el estado. El servidor no "recuerda" quién sos entre un pedido y otro. Por eso hacen falta mecanismos externos como las cookies para sostener la sesión.

11) ¿Qué nueva versión se está usando para mejorar la velocidad?

HTTP/2 (RFC 7540, desde 2015). Es un protocolo binario que conserva la misma semántica que HTTP/1.1 (mismos verbos y cabeceras) y aporta:

  • multiplexación de requerimientos sin esperar respuesta

  • frames binarios en lugar de texto

  • compactación/compresión de headers

  • prioritización programable de los elementos requeridos

  • server push (entregas multiplexadas)

Está basado en ideas del SPDY de Google. Requiere TLS en la práctica: sin HTTPS no es viable.

12) ¿Cómo mejora una app web en ambientes ruidosos o de conexión débil?

Con HTTP/3 sobre QUIC (2019). QUIC hace sobre UDP el trabajo que hacía TCP (datos fiables y seguros) pero de forma más eficiente, con conexiones mucho más cortas. La mejora ahí no es tanto la velocidad de transmisión sino la capacidad de reconexión inmediata ante caídas por ruido ambiente, exceso de tráfico o baja cobertura (industrias, aeropuertos, zonas alejadas de las ciudades).
